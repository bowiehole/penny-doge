# Penny DOGE: fleet usage inventory (generic, ships with the template)

*Signals, gaps, advice catalog and design for Penny DOGE. Owner-specific findings, the roster, the outcomes log and Penny DOGE's own-cost table live in `local/inventory_local.md`, which never ships.*

Penny DOGE's job: find wasted usage across an owner's bots and tell them what to cut. It only recommends. It never pauses, edits, or deletes anything itself.

## 0. Freshness of each local source (read this first)

| Source | Path | What to expect | Reliability |
|---|---|---|---|
| Routine definitions | `agents/<id>/automations/<slug>/automation.json` | Synced snapshots. `lastRunAt` and `enabled` can lag live state by weeks; a routine deleted or paused live can still look enabled on disk. | **Low for current state.** Good for history and prompt text. Check live status before advising. |
| Run history | `automations/<slug>/runs.json` | **Capped at the last 20 runs.** | Low for counts. Use it for status and errorKind only. |
| Chat store | `agents/<id>/store.db` (`transcript_entries`, `kv`, `automation_completion_inbox`) | Snapshot; many bots may have an empty local store. | Medium for patterns, low for now. Copy the `-wal` too: some live `unreadState` values only appear there. |
| Model transcripts | `agent-transcripts/<id>/<id>.jsonl` + `sand-subagent-*` folders (routine runs among them) | Same snapshot. Lines have **no per-message timestamps**. | Medium. The only source for quiet vs. surfaced runs and model calls per run. |
| Audit log | `agents/<id>/audit.jsonl` | Snapshot. Holds only `shell_command`, `mcp_tool_call`, `browser_navigation`, `computer_use_session`. | Medium for history. |
| Memory logs | `agents/<id>/memory/log/YYYY-MM.md` | Synced; shows memory bloat from routines. | Medium. |
| Global settings | `agent-data/settings.json` | Usually live. Pinned bots, sidebar sections, notifications on/off. | High. |
| Profiles | `agents/<id>/profile.json` | Some are live. | High for the bot list and descriptions. |
| Grok Build CLI sessions | `~/.grok/sessions/**` + `grok usage <id>` | **Live.** | **High: exact tokens and cost**, but only for coding work sent to the CLI. |

## 1. Signals we can monitor

| # | Signal | Source | How to compute | Freshness / reliability |
|---|---|---|---|---|
| 1 | Schedule and runs per week | `automation.json` `.schedule` / `triggerPresentation.trigger` | Expand the cron (min × hour × dow) to runs per week. `webhook` means event-driven. | Definitions can be stale (see §0). |
| 2 | Enabled / paused | `automation.json .enabled`, plus `event` entries `automation-changed` (created / enabled / disabled / updated) in store.db | Direct read. The event history shows churn. | Stale locally. |
| 3 | Last run and failures | `runs.json` `{startedAt, finishedAt, status, errorKind/detail}` and `automation.json .lastRunAt` | Failure rate = non-ok / runs. Median duration. | Last 20 runs only. |
| 4 | **Quiet vs. surfaced run ratio** | Routine-run subagent transcripts (first line says `[routine] "<name>" (folder <slug>) … fired <time>`) | A run surfaced if it called `WakeParent` or `SendToAgent` (shown as `communicate_update` with `"tool":"WakeParent"`). Otherwise it was quiet. | Snapshot only, but complete within it. |
| 5 | Model calls and token proxy per run | Same transcripts | Model calls = count of assistant lines. Replay proxy = Σ (transcript bytes before each assistant line) / 4. This leaves out the system prompt and memory, which every call also pays for. | Proxy, not billed tokens. Cache discounts are ignored. |
| 6 | Parent revival (second cost of a surfaced run) | store.db `send-message` with `"wake":"background-revival"` | Each `WakeParent` restarts the parent bot's turn on its long main chat. Count wake bursts (by requestId). | Snapshot. |
| 7 | Duplicate jobs across bots | All `automation.json` + completion texts in `automation_completion_inbox` | Same cron and overlapping prompt keywords on 2+ bots. Also completion text like "X already ran…finished quietly". | Good. |
| 8 | Stale one-time or finished routines | Slugs in run transcripts with no `automation.json`, plus prompts with dated or one-shot language | A slug ran but no longer exists (deleted). Or it exists with a past date. | Good. |
| 9 | Prompt has a quiet rule | `automation.json .prompt` | Regex `stay quiet / no filler / nothing new`. | Good. |
| 10 | Message volume per bot | store.db `transcript_entries` | `message role=user` without `fromAgent` = **human**. With `fromAgent` = agent→bot. `message role=assistant toAgent` = bot→agent. `send-message` = bot→user (`message.type` text, widget, attachment, local-tool-permission…). | Snapshot. |
| 11 | Reply rate and latency (engagement proxy) | store.db timestamps | For each bot message (or wake burst), the next human message in that bot within 2h or 24h, and the median minutes. | Proxy. A reply may be about something else. |
| 12 | Widget answers | `send-message` widget + `respondedValue` / `widgetSkipped` / `widgetDismissed` | answered / skipped / dismissed. | Snapshot. |
| 13 | Reactions (tapbacks) | `send-message.reactions = [{emoji, by:"me"}]` | Count per bot. There is no reaction timestamp. | Exists but rare. |
| 14 | Bot-level "last opened" | kv `unreadState` = `{lastActivityAt, lastUnreadActivityAt, lastViewedAt, isManuallyUnread, unreadCount}` | Seen-after-activity = `lastViewedAt ≥ lastActivityAt`. Days since last opened. | Latest value only, no history. The live update shows only in the WAL for some bots. Sync may bump it, so treat with care. |
| 15 | Progress chatter | store.db consecutive bot text messages between human messages | Messages per burst (median and max). Short "on it / checking / kicked off" style lines under 220 chars. | Heuristic. |
| 16 | Turns per day (cost proxy) | kv `requestIds` (`[{id, at}]`) | Count / span of days. These are main-thread turns, including wake revivals and agent messages. They are **not** routine subagent runs (0 overlap with runs.json). | **Rolling cap of 200**, so it's a rate, not a total. |
| 17 | Spend initiations | `spend-initiation` entries (`initiation.id` = `t<N>u` user msg, or `offrec-*`) | Count per bot. | About one per human-started turn. Routines are not included. |
| 18 | Subagent fan-out | `task` tool calls in transcripts, plus subagent folder count | Count per bot and per routine. | Snapshot. |
| 19 | Memory bloat from routines | `memory/log/*.md` size, lines written per routine | Bytes and lines per routine per week. Memory goes into every prompt. | Good. |
| 20 | Main-chat size (long-chat flag) | `agent-transcripts/<id>/<id>.jsonl` bytes | MB per bot. Flag routines that wake a bot whose chat is long. | Snapshot. |
| 21 | **Exact tokens and cost: Grok Build CLI** | `grok usage <session-id>` (run from the session's cwd). `~/.grok/sessions/*/<id>/summary.json` gives cwd, title, request_id. | Sum `totalTokens` and `costUsdTicks` per cwd and map each repo to its bot. | **Live and exact**, but only for CLI coding work. The tick unit is undocumented: $ figures assume 1 tick = 1e-10 USD, so verify. |
| 22 | Fleet roster and grouping | `profile.json`, global `settings.json` (`pinnedAgentIds`, `sidebarSections`) | List, pinned, section, created, last activity. | Live. |
| 23 | Orphaned transcripts | `agent-transcripts/<id>` with no `agents/<id>` | Folder exists with no agent dir. | Good. |
| 24 | Tool mix per bot | `audit.jsonl` types, MCP `durationMs` | Counts per bot and week. | Snapshot. |
| 25 | **Always-on load** (text carried on every turn) | `profile.json .description` (live); store.db kv prompt snapshots `agentProfilePromptSnapshot`, `promptSectionSnapshots`, `promptPrefixSnapshot` (read by key; lengths only); `memory/profile.md`, `user-memory/by-agent/<id>/profile.md`, `projects/*/memory/by-agent/<id>/profile.md`; `automation.json .prompt` + #1 fire rate | Instruction chars + memory chars (rendered memory section, else profile.md files) + visible platform section chars; tokens = chars/4. Routine prompt chars × fires/wk. Re-send $ = load × model calls/wk + prompt × fires × calls/run at the blended rate. | Instructions live; snapshots are as old as the bot's last synced turn. Estimate. |

## 2. Signals we can't get today, and workarounds

| Missing | Why | Workaround |
|---|---|---|
| **True per-message read receipts** | Only bot-level `unreadState` (latest `lastViewedAt`, `unreadCount`), with no history and no per-message read flag. If push notifications are off (`notifications.isEnabled=false`), there's no delivery or open signal either. | (a) Penny DOGE saves a snapshot of `unreadState` on each run to build a history. (b) Use reply, widget, and tapback rates (#11–13) as the stand-in. (c) Treat "opened but no reply after N messages" as soft-ignored. |
| **Exact per-bot Grok Bot token or credit spend** | No token or credit fields anywhere in store.db, transcripts, audit, or runs.json. The Usage page has no known API. (Credit-balance tool calls in transcripts may belong to third-party APIs, not Grok.) | (a) Bytes→token replay proxy plus model-call counts (#5). (b) Weekly screenshot or paste of the Usage page, which Penny DOGE parses. (c) Exact numbers exist for Grok Build CLI work (#21), so push heavy coding through the CLI and attribute by repo. (d) Calibrate the proxy against CLI sessions, where context and billed tokens are both known. |
| **Live routine state for other bots** | Local `automation.json` is a stale snapshot. UpdateRoutine only manages the calling bot's own routines. | ReadTranscript each owned bot and parse `automation-changed` events and the latest routine results. Ask the user to confirm status from each bot's routine panel. Or ask each bot to report its own routines (only with approval). |
| **Full run counts** | runs.json keeps 20 entries. requestIds keeps 200. | Count routine subagent transcripts, which hold the full history. Penny DOGE also keeps its own weekly ledger in `ledger/`. |
| **Cost of a parent revival** | The size of the revived turn isn't recorded. | Proxy = number of wake bursts × parent chat size. |
| **Data for bots with empty local stores** | Never synced locally, or brand new. | ReadTranscript before calling any of them idle. **Never recommend deleting based on local emptiness alone.** |
| **Model and reasoning effort for bots and routines** | Every bot profile shows only the harness (`temporal`); routine definitions and transcripts don't record the model or effort used. Only Grok Build CLI sessions record `current_model_id`, `reasoning_effort`, and per-message `model_id`. | A19 covers CLI coding only. For bots and routines, ask the owning bot, or read the Usage page if it ever shows a model breakdown. |
| **Per-message timestamps in model transcripts** | Not present. | Join to store.db timestamps by `messageId`, or to the routine `fired` time in the first line. |

**Always-on load (A21): what is and isn't visible locally** (checked Oct 2, 2026; sizes and counts read, not contents)

| Item | Visible? | Where / notes |
|---|---|---|
| Bot instructions | **Yes, live** | `profile.json .description` (every bot; the only instruction-like field). Other profile keys are cosmetic (name, title, avatar, harness). |
| Per-bot settings | Yes, but trivial | `agents/<id>/settings.json` holds only notification and voice flags; nothing that adds prompt text. |
| Routine prompts + fire rate | **Yes** | `automation.json .prompt` (length), `.schedule` cron → fires/wk; event triggers use the observed run rate. Snapshot (can lag live). |
| Profile-tier memory | **Yes** | `memory/profile.md` (bullet lines = facts), plus `user-memory/by-agent/<id>/profile.md` and `projects/*/memory/by-agent/<id>/profile.md` when present. Monthly history is in `memory/log/YYYY-MM.md` (not always-on). |
| Rendered prompt sections | **Partly, as of the bot's last synced turn** | store.db kv `promptSectionSnapshots` gives the rendered length of `memory`, `automations`, `agent_directory`, `mcp_instructions` (and sometimes `timezone`); `agentProfilePromptSnapshot` gives the profile section length. Only bots with a synced chat have them. |
| Other prompt sections | **No (names and hashes only)** | `promptPrefixSnapshot` lists ~14 sections (base, spotlight, profile, user identity, multitask, timezone, memory, automations, skills, agent directory, MCP instructions, remote box, computer, …) and a tool count, but only as hashes; their sizes aren't visible. |
| Attached skills | **No per-bot list** | Bot-written skills in `memory/skills/*.md` are visible (count + size). The shared skill library (`workflows/*/SKILL.md`) and managed or plugin skills are visible fleet-wide, but which ones each bot carries in its `skills` section isn't recorded. |
| Tool schemas | **No** | Only a tool count and hashes; schema text isn't stored locally. |
| Does a routine run carry the bot's instructions + memory? | **Unknown** | A21 counts routine runs as carrying only their own prompt (a lower bound for routines). |
| Store `metadata` | Never read | Off limits by design (it holds an encryption key). |

## 3. Advice catalog (trigger → recommendation)

Thresholds are starting points. Tune them after 2–3 weekly runs. "Calls/wk" = model calls per week from #5. Savings are estimated as calls/wk removed and replay tokens/wk removed.

| ID | Recommendation | Triggering signal(s) | Threshold |
|---|---|---|---|
| A1 | **Pause or rearm idle watchers.** Pause until a condition is true, e.g. "re-enable when a position is filled" | #4 quiet ratio, #19 memory says "idle / no X" | ≥95% quiet over ≥20 runs **and** the completion text repeats the same idle reason |
| A2 | **Cut cadence** (5-min → hourly, 3×/day → 1×/day, daily → weekdays) | #1 runs/wk, #4 | Runs/wk ≥ 50 **and** surfaced ≤ 10%. Or any cron denser than hourly. |
| A3 | **Switch to event triggers** (webhook, Gmail, GitHub) instead of polling | #1 + prompt says "check if X happened" | Polling routine with ≥80% quiet when an event source exists |
| A4 | **Fold into one digest** (several briefs from one bot within 2h → one) | #1 times, #11 reply rate | ≥3 routines from the same bot within 120 min **and** reply-within-24h < 25% |
| A5 | **Remove a duplicate job** (keep one owner, others subscribe) | #7 | Same cron ±30 min on 2 bots with ≥40% keyword overlap, **or** a completion that says "already ran / already relayed" |
| A6 | **Quiet when nothing new** (add a stay-quiet rule, plus a cheap pre-check before the deep dive) | #9 missing rule, #4 | Prompt has no quiet rule **or** surfaced runs whose text is "no change / idle" ≥ 2 per week |
| A7 | **Cheap gate first** (a shell, API, or diff step before research, ending early if unchanged) | #5 calls/run, #4 | ≥25 model calls/run **and** ≥40% quiet |
| A8 | **Merge a watchdog into its producer** (the job reports its own failure) | #7 (routine A checks routine B's output) | Watchdog surfaces in ≤30% of runs |
| A9 | **Delete stale one-time routines** | #8 | One-shot or dated routine past its date, or a finite watch past its end condition. Still enabled after 7 days. |
| A10 | **Pause routines nobody reads** | #11, #12, #14 | Wake bursts with 0 human replies, widgets, or tapbacks in 14 days, **or** a bot not opened for 14 days while its routines keep surfacing |
| A11 | **Shorten progress chatter** (one final message per task, no "on it / still working") | #15 | Median burst > 4 msgs, **or** max burst > 15 with no human message, **or** progress-like share > 15% |
| A12 | **Move standing routines off long chats** (a fresh bot with a short chat owns the sweep) | #6 + #20 | A routine that surfaces into a main chat > 10 MB |
| A13 | **Trim memory logging from routines** (log only changes, roll up idle notes) | #19 | One routine writes > 20 memory lines/wk, or the memory log is > 30 KB |
| A14 | **Merge or retire overlapping or idle bots** | #10, #14, #22 descriptions | No human message and not opened for 30 days (after a live ReadTranscript check), **or** two bots whose descriptions claim the same beat |
| A15 | **Cut fan-out** (fewer subagents per run) | #18 | > 2 `task` spawns per routine run on average |
| A16 | **Fix flaky routines before they retry-burn** | #3 | ≥2 errors in the last 10 runs, or repeated `provider_overloaded` at the same time slot (move it by a few minutes) |
| A17 | **Batch CLI coding sessions** | #21 | One repo > 25M tokens/wk, or > 5 sessions/day on one repo |
| A18 | **Retime to reading** (move the routine to when the owner actually reads, or fold it into a digest at that hour) | #4 surfaced runs, #11 next human message + its hour of day | Median delay from a surfaced run to the next human message in that bot ≥ 4h over ≥ 4 samples (delays > 72h count as unread, not slow), schedule ≤ 1 fire/day, and the typical reply hour is ≥ 2h from the fire time. Suggest a cron at the median reply hour. |
| A19 | **Lighter model or effort for small coding sessions** | #21 CLI sessions: `summary.json` `current_model_id` / `reasoning_effort`, `chat_history` `model_id` | Over 30 days, ≥ 3 sessions in one repo, median tokens/session < 300k, and ≥ 50% of sessions at high/xhigh/max effort (or a model on the configured heavy list). CLI only: bot and routine model choice isn't visible locally (§2). |
| A20 | **Reset bloated chats** (summarize and reset, or move routines to a fresh short-chat bot) | #20 main-chat MB, #16 turns/day, #6 routine wakes | Main chat ≥ 15 MB **and** ≥ 1 turn or routine wake per week. Est. savings = (turns + wakes)/wk × calls/turn × (size-based replay proxy, capped at the context window, minus a fresh-chat baseline). |
| A21 | **Trim always-on load** (move how-to detail into skills, keep profile memory small and push history to the log, prune stale facts, keep routine prompts short by pointing to files) | #25 always-on load, #1 fires/wk, #16 turns/day | **Owner-written text only:** instructions + memory > `max_always_on_tokens` (default 4,000), **or** a routine prompt > `max_routine_prompt_tokens` (default 1,500) that fires ≥ daily. The app's own sections (bot directory, routine and connector guidance) are shown in the report for context but never flagged (`count_platform_sections: false`): they grow with fleet size and owners can't trim them, and counting them flagged nearly every bot. Weekly re-send $ shown as an estimate. |
| A22 | **Claim new coding folders** (stub; implemented as repo claims + `unmapped_ask`, not a ranked candidate) | CLI sessions in a repo missing from the owner repo map | Normal flow: the coding bot claims its own named folder by messaging Penny DOGE once ("map <repo> → me"); Penny runs `claim_repo.py`, which writes the map. The owner is asked only when unclaimed coding older than `claim_grace_days` (3) is large (≥ `min_usd` $10, or ≥ `min_share` 25% of coding and ≥ $5), or when two bots claim the same folder. Never guessed. |

## 4. Proposed Penny DOGE design

**Shape:** two halves. A box cron does all the counting with **no AI**. A model only wakes when something is over threshold.

**1. Weekly no-AI scan (box cron, Monday 07:05 box-local time):** `5 7 * * 1 /bin/bash <doge>/weekly_scan.sh >><doge>/cron.log 2>&1`, installed by the idempotent `install.sh`. Bash + Python only, **0 model tokens**:
1. `run_all.sh` re-runs the read-only scans (copies sqlite to `/tmp`, writes JSON).
2. `summarize.py` saves a compact snapshot to `history/YYYY-WW.json` (per routine: runs, surfaced, quiet %, calls/run, runs/wk; per bot: unreadState, chat size, memory-log size; CLI tokens/cost for the last 7 days) and diffs it against the previous week.
3. It applies the §3 thresholds as plain code. All numbers live in `config/thresholds.json` (none in code). Implemented: A1, A2, A4, A5, A6, A7, A9, A10, A13, A15, A16, A17, plus the idle half of A14 (step 5a). Skipped (needs prompt or description semantics): A3, A8, A11, A12, and A14's overlapping-descriptions half.
4. **Staleness guard:** a signal whose newest underlying run is older than `stale_days` (default 10) is marked `stale` and can never wake the model. It is listed only in `stale_watch`. Each item is also flagged `new_or_worse` vs. last week (new, or est. savings ≥ 2×).
5. It writes `summary/latest.json` (+ a dated copy), **at most `output.summary_max_bytes` (default 7,000 bytes)**: week, data freshness per source, CLI spend last 7d, Penny DOGE's own cost fields, and at most 5 `candidates` ranked by est. runs/week saved (bot, bot id, routine, advice ID, signal + number, est. saving, one-line change, a plain `why` sentence, stale / new_or_worse flags). Names and counts only.
5a. **Idle-bot tracking (A14, decommission candidates):** for each bot it computes days since the owner last viewed it (unreadState `lastViewedAt`), days since the last human message in its local store, whether it has enabled routines, and recent CLI sessions mapped to it through the owner's repo→bot map. A bot is listed in `idle_bots` (max 8) only when **both** the viewed and human-message signals are past `idle_bots.min_days_unused` (default 30). Bots past `warn_days` (default 21) go in a short `idle_warn` name list. Bots with an empty local store or no unreadState are never called idle: they go in `idle_unknown` (names only). Penny DOGE's own bot and the owner's `keep_bots` are excluded. The ledger records idle bots once a wake has gone out, and a bot is re-raised only when its idle days double. Idle bots never trigger a wake by themselves. **Guardrail:** a bot is listed idle only when its local store is fresh (newest entry within `stale_days`), at least `min_signals` (2) local signals agree (view stamp and last human message both past the threshold), and no CLI session mapped to it falls within `warn_days`. Recent coding counts as use. Stale stores go to `idle_unconfirmed`: names only, no day counts. Unread senders from stale stores are counted, not listed. The summary carries `idle_rule` (the wording rule) for the wake. The wake mentions them only as "confirm live, then ask the owner"; a bot is never retired on local evidence.
5b. **Unread sender:** a bot that keeps messaging the owner while the owner isn't opening its chat. From unreadState (`lastViewedAt`) and the store's bot→user `send-message` timestamps, it counts messages sent after the last view and the days since that view. A bot is flagged when it sent ≥ `unread_sender.min_unseen_msgs` (default 3) messages after the last view **and** that view is ≥ `min_days_unviewed` (default 14) days old. It's listed in `unread_senders` (max 5: name, id, unseen_msgs, days_unviewed, has_routines). Bots without unreadState, Penny DOGE's own bot, and `keep_bots` are skipped. Unlike idle bots, a **fresh** unread sender (newest unseen message within `stale_days`) that hasn't been raised before makes the wake a `report`. The ledger records it only after a successful POST and re-raises it only when unseen_msgs doubles.
5c. **Per-day consumption table:** `daily_usage.py` (run by `run_all.sh`) and `summarize.py` build a bots × Mon–Sun table for the most recent full week (`daily_usage.week`: `last_full`, or `current` for the partial week). **CLI cells are exact**: Grok Build tokens and $ from `grok usage` per-turn `endedAt`, attributed to bots via the owner's repo map. Unmapped repos go to an "Unmapped CLI" row, and resolved repos are still attributed but never raised. **Chat + routine cells are labeled estimates**: routine runs use the #5 replay proxy, and chat uses #16 turns/day × the bot's average calls/turn, with replay per call capped at `context_cap_tokens`. Days after a bot's newest local data show `n/a`, not 0; † marks chat-only cells for bots whose routine runs aren't local. Output: a compact `daily_usage` block in `summary/latest.json` (top `top_bots` + "Other", tokens in k) and a ready-to-post `summary/daily_table.md` with a freshness line. With `wake.always_weekly_cost` on, every Monday POSTs (`cost_only` on quiet weeks), so the table goes out weekly.
5d. **Spend split (default `daily_usage.table_layout: split_spend`):** the Markdown leads with one per-bot table, Coding $ (exact) | Bot work ~$ (estimate) | Total, plus a Totals row and an overall line (`coding $Y · bots ~$X · total ~$Z`). **Graceful degrade:** when fewer than `daily_usage.min_bot_coverage` (default 0.5) of bots have local activity data newer than `stale_days`, bot-work $ is hidden everywhere (overall, monthly, week-over-week, movers, JSON) and one plain sentence says why; only exact coding is shown. Bot work converts the estimates to dollars with a configurable price (`estimates.bot_usd_per_m_tokens`, or separate input/output prices); the default is the per-token rate implied by the exact CLI data. Then comes "Coding by day (exact)". The older two-table layout stays selectable as `by_day`, and `summary.daily_usage.totals` carries `bots_usd_est`, `coding_usd`, and `total_usd_est`.
5e. **Week-over-week trend:** `trend.months` (default 1) becomes N = ⌈months × 4.3⌉ full Mon–Sun weeks. Each run rebuilds per-week coding $ (exact, backfilled from CLI per-turn data back to its first record) and bot work ~$ (estimate, local data), per bot and overall. It merges them idempotently into `history/weekly_totals.json`: a fresh value overwrites, a missing value never erases a stored one, so trends outlive the 20/200 caps and stale stores. The Markdown gets a "Week over week" table after the overall line (Coding $ | Bots ~$ | Total | change ±$/±%, comparing full totals only when bot-data coverage is similar, otherwise coding only) plus the top 3 movers. The summary gets a compact `trend` block. Missing weeks show `n/a`, never 0.
5f. **New advice in the weekly scan:** A18 retime-to-reading (per routine: fire time, median read delay, typical reply hour, suggested cron), A19 heavy model/effort on small CLI sessions, and A20 chat bloat. Thresholds live in `config/thresholds.json` under `advice.A18`–`A21`. A21 always-on load comes from `always_on.py` (lengths only) and adds an "Always-on load" table to daily_table.md.
5g. **Monthly line + early warning:** month-to-date coding $ (exact) and bot work ~$ (estimate), projected month-end at the trailing `budget.rate_days` daily rate, and the change vs last month. The owner can set `budget.monthly_usd`, `credit_balance_usd`, and `balance_as_of` in `local/owner.json`. With a balance set, runway = (balance − spend since as-of) / daily rate. `warn` fires when runway < `budget.warn_days` or the projection exceeds the budget, and a warning makes the wake a `report`. Routine errors matching `budget.outage_regex` (overloaded, rate, quota, credit, token) in the last 7 days are noted as possible outages. The summary gets a one-line `monthly` block, and the Markdown gets a line under the overall line.
5h. **Daily template-install check (`new_bot_check.py`, box cron 07:35 box-local time, no AI):** it keeps `local/known_bots.json`, seeded on the first run with nothing flagged. A new bot, or a new routine on a bot first seen within `watch_days`, is flagged when it's a scheduled AI routine denser than hourly or polls on a schedule with no quiet rule; webhook/event triggers count as good. Only then does it write `summary/new_bots.json` and POST `{"mode":"new_bot_check","bot":...,"summary_path":...}`. Otherwise it stays silent. `--dry-run` writes nothing (not even the seed); install.sh seeds with `--seed`.
5i. **Fleet-wide daily spike guard (`spike_guard.py`, run by the same 07:35 cron, no AI):** per enabled routine, from local routine-run transcripts (fired time, model calls, replay proxy), it compares the last 24h with the trailing daily average over `spike_guard.baseline_days` (default 14; needs ≥ `min_baseline_days` of history). **Spike** = runs or est. $ ≥ `factor` (2.0) × baseline and above floors (≥ 6 runs and ≥ 4 extra, or ≥ $0.50/day). **Loop** = ≥ `loop_min_runs` runs inside `loop_window_min` that exceed `loop_schedule_factor` × what the cron allows (event routines: the run count alone), or `fail_repeat` identical consecutive failures in runs.json, with the latest one in the window. **Stale data never alerts**: the newest routine-run transcript must be within `max_data_age_hours` (36). Each routine+kind wakes at most once per `cooldown_days` (ledger/spike.json, written only on a real run). One POST total: `{"mode":"spike","summary_path":"summary/spike.json","count":n}`; the wake sends one short message (routine, the jump, why it costs money) and asks the owner before contacting the owning bot.
5j. **Alert level (`local/owner.json` `alert_level`):** `quiet` / `normal` / `chatty` maps to config overrides in `alert_levels` (quiet: top 3, re-raise at 3×, spike guard 3×; normal: no overrides; chatty: top 8, re-raise at 1.5×, spike guard 1.5×, a cost note on quiet weeks). Applied in summarize.py, wake.py and the spike guard. `normal` is a no-op, so output is unchanged.
5k. **Usage-page calibration (`calibrate.py`, no AI):** the bot reads the owner's pasted text or screenshot of the app's Usage page (% remaining, reset date, $ if shown) and runs `calibrate.py --pct-remaining N [--reset D] [--remaining-usd X] [--plan-usd Y] [--at T]`. The script computes the burn rate (vs the previous reading, or since the period start if it's the first), the projected run-out date vs the reset date, and the gap ratio of observed usage ($ = used % × plan $, or the change in remaining $) to Penny DOGE's own estimate over the same window (exact coding + estimated bot work). It appends every reading to `local/calibration.json` (owner-local, never ships). The bot correction factor = (observed − coding) / bot estimate, only when bot-data coverage ≥ `calibration.min_bot_coverage`; it's the rolling median over the last `rolling_n` readings, clamped to `clamp`. summarize.py multiplies bot ~$ by it and labels the report "calibrated ×F" only once ≥ `min_observations` (2) readings exist; with none, the output is byte-identical. **Auto-slowdown** (`auto_slowdown {below_pct, bots}`) is OFF by default. Only the owner can turn it on, in chat, by naming the % and the bots. When it's on and remaining % drops below the threshold, the bot may send only those named bots a slow-down request without asking first, and must tell the owner right after. It never edits their routines.
5l. **Quick audit on first chat (`quick_audit.py`, no AI):** before any cron or webhook exists, it refreshes the collectors and names the top 1–3 likely burners: heavy routines (calls/run, replay, cadence, quiet %, long-chat wakes) and at most one long chat (its $ is an upper bound), each with one why line. It skips owner-handled/excluded bots and Penny DOGE itself. Output: `summary/quick_audit.md` / `.json`, plus a note when the local data is old.
6. **Wake decision:** POST to the webhook only if at least one non-stale candidate is new or wasn't raised before. `ledger/raised.json` tracks raised and skipped items, and an item is re-raised only if it gets 2× worse. Owner-handled items from `local/owner.json` are seeded as skipped. If the webhook isn't configured, it logs that and exits 0. If the POST fails, the body is appended to `wake_queue.log`. `--dry-run` does everything except the POST. `--probe` sends `{"probe": true}` and prints only the HTTP status.
7. Every run appends start/end, wall seconds, candidate counts, and posted yes/no to `cron.log`, so Penny DOGE's own cost stays visible.

**2. Webhook routine `Penny DOGE threshold wake` (on Penny DOGE's own fresh bot with a short chat):** woken only over threshold, never on a schedule.
- Reads **only** `summary/latest.json`. It doesn't re-run scans or read raw JSON or transcripts.
- **Live-confirms** at most 5 wins with the owning bots (current routine state: enabled/paused, last run) before reporting anything. A win that fails the live check is dropped and recorded as skipped in the ledger.
- Sends **one short message per confirmed win** (bot › routine, signal + number, savings, one-line fix, approve/skip). No "(no change)" messages.
- Budget: **~15 tool calls max, no subagents.** Ignore bodies with `"probe": true`.
- Modes: `report`, `cost_only`, `new_bot_check`, `spike` (see template/routine_prompts.md). Chat instructions in the same file cover the quick audit, Usage-page calibration, auto-slowdown and the alert level.
- Records its own tool calls / messages into the owner's *Penny DOGE own cost* table (`local/inventory_local.md`).

**Portability (template):** generic pieces ship as is: scripts, `config/thresholds.default.json`, `config/owner.example.json`, `install.sh`. Owner data stays local and never ships: `local/owner.json` (exclusions, already-handled items, repo→bot map, redact terms), `ledger/`, `history/`, `summary/`, `.webhook.json` (url + key, chmod 600). First run on a new fleet: `bash install.sh`, create the webhook routine, `bash setup_webhook.sh` (one probe; saves `.webhook.json` only on a 2xx), then follow FIRST_RUN.md. See template/MANIFEST.md for what ships.

**Guardrails**
- Recommend only. **Never pause, edit, delete, or message another bot without the owner's explicit approval of that specific change.** A bot can only UpdateRoutine its own routines; on approval, Penny DOGE gives the exact change for the owning bot.
- Never call a bot idle or orphaned on local evidence alone. Stale local signals never wake the model. Confirm live first.
- Always show data freshness. Flag snapshot-only conclusions.
- Privacy: bot and routine names and counts only. No message contents, no family or child names, no email addresses, no secrets. Never decode or print `metadata` (it contains an encryption key). Never read credential files. Never echo the webhook key.
- Budget: a quiet week costs 0 model tokens. A wake has a hard cap of ~15 tool calls and 0 subagents. If Penny DOGE's own cost exceeds the smallest win it reports, it says so and cuts its own cadence (biweekly).
- Don't send the same recommendation twice (ledger; re-raise only at 2× worse).

## 6. Template notes (generic lessons only)

- **Local snapshot files lag live routine state by weeks.** A routine paused live can still look enabled and busy in local definitions and run history. Every signal sourced from local files (#1–#9, #15–#20, #24) needs a live confirmation from the owning bot before it becomes a reported win. Ask the bot for its current routines (enabled/paused, last run) first; that one message is cheaper than a wasted recommendation.
- **Idle-bot signal (A14) needs both "not viewed" and "no human message" for 30+ days.** Either one alone is noisy: sync can bump `lastViewedAt`, and some bots are read but never typed into. Bots with an empty local store or no unreadState are "unknown", not idle. Track idle days in the ledger and re-raise only when they double, so the same bot isn't nagged weekly.
- **Unread sender (messages piling up after the last view, last view ≥14 days old) is the cheapest "nobody reads this" signal.** It needs only unreadState plus send timestamps, so it works even when reply data is thin. Count only messages *after* `lastViewedAt`, skip bots with no unreadState, and let only fresh senders wake (stale stores can show old piles that were already handled).
- **Per-day table: keep exact and estimated numbers in separate tables, and show `n/a` for days past each source's freshness.** CLI usage is exact and live; chat/routine numbers are proxies from local snapshots that can lag weeks. Mixing them, or printing 0 for missing days, overstates confidence. Attribute CLI spend by an owner-maintained repo→bot map and list unmapped repos so the map gets filled in.
- **A18 needs a meaningful shift:** a routine that already fires at the owner's usual reply hour but is read a day or two later is an attention problem (A10), not a timing problem, so require a ≥ 2h shift before suggesting a new cron.
- **A19 only sees CLI coding.** Model and effort for bots and routines aren't recorded locally. Don't infer them; ask the owning bot.
- **A20: big chats are common, and the cost only matters while turns or wakes keep arriving.** Gate on recent activity, and report the savings as a replay proxy capped at the context window.
- **Monthly projection: use a trailing 7-day rate, not month-to-date.** Early in the month, MTD/day is noise. Show "coding-only" when bot-work estimates are missing, and keep budget and balance owner-set (blank by default).
- **New-bot check: seed first, flag only new things, stay silent otherwise.** A daily no-AI check is nearly free. A POST only when a fresh install adds a dense or quiet-rule-less schedule catches template misuse early.
- **Graceful degrade when bot data is thin (Oct 2 pre-publish).** If fewer than `daily_usage.min_bot_coverage` (default 0.5) of bots have local activity data newer than `freshness.stale_days`, the report shows exact coding (CLI) numbers only: no Bot work ~$ column, a coding-only overall/monthly line, a coding-only week-over-week table and movers, plus ONE plain sentence saying what's hidden and why. latest.json carries `bots_hidden`, `bots_hidden_why` and `bot_coverage: [fresh, total]` and nulls the bot $ fields so the wake can't quote blanks. Full columns come back on their own when coverage recovers; history/weekly_totals.json keeps the bot estimates either way. Coding leads in every layout because it's the exact number.
- **Every candidate carries a `why`:** one plain sentence on what looked wasteful and why it costs money (fixed text per advice ID, no owner data). A20's says old history gets summarized, so the $ is an upper bound, and to save learnings to memory/skills/a file before any reset.
- **One webhook module.** `doge_webhook.py` is the only place that cleans the key (strips `Authorization:` and `Bearer `, a lone `Bearer` counts as empty), sends both auth headers, and never prints the key or URL. wake.py, new_bot_check.py and setup_webhook.sh all import it.
- **Webhook setup is a walkthrough with a probe.** `setup_webhook.sh` takes URL + key (prompt with hidden key entry, or env DOGE_WEBHOOK_URL / DOGE_WEBHOOK_KEY), sends ONE `{"probe": true}`, and writes .webhook.json (chmod 600, old file kept as .webhook.json.bak) **only after a 2xx**. Lesson learned the hard way: an earlier version wrote before probing, and a bad test input replaced a working config. On 401/403 it explains that the key is wrong or regenerated (re-copy the Webhook key field, paste only the key). `--use-existing` re-checks without a prompt.
- **First-run docs ship with the template:** README.md (does / never does, install, webhook, knobs, data limits), FIRST_RUN.md (first message + optional budget/balance, repo→bot map, keep_bots questions), and `template/` (manifest, settings check-in skill, routine prompts). The settings check-in routine gets created once on first run, 14 days out.
- **Bots claim their own coding folders; don't spam the owner.** A coding bot that starts a new repo messages Penny DOGE once: "map <repo> → me". Penny runs `claim_repo.py --repo <repo> --bot-id <id>`, which writes `cli_repo_bots` in local/owner.json. It is idempotent, refuses bare roots, and never overwrites another bot's mapping (that goes to `cli_repo_conflicts`). The owner is asked only when unmapped coding is large AND still unclaimed after a grace period, or a folder is claimed twice. Then latest.json carries `unmapped_ask` and the wake puts it first in Worth a look: "Why I flagged it: this coding spend isn't linked to a bot yet, so the report can't show who ran it." Once mapped, the next scan attributes the spend, and recent coding counts as proof of use for the idle check. Folders with 0 tokens are never asked about.
- **Named project folders, never bare roots.** Coding bots run Grok Build from a stable folder named for the product (`/workspace/<product>`), never the bare `/workspace` or home folder. Sub-folders map through the first folder name, and a bare root can't be claimed.
- **Never call a bot unused or unviewed from one stale stamp.** Local per-bot stores (unreadState, transcript) are sync snapshots and can stop updating for weeks while the owner keeps chatting with the bot live (phone or app). Seen in practice: a bot the owner messaged two days earlier still showed a month-old view stamp, but its coding sessions that same evening were on the box. Rules: (1) idle needs a fresh store plus ≥ 2 agreeing signals and no recent coding; (2) stale stores are "not judged", never "N days unviewed"; (3) the wake says "local data shows no owner activity since <date> (unconfirmed)" and asks the owning bot before suggesting retirement; (4) any recent use signal (CLI, view, human message) wins over an older one.
- **A20 standard fix:** before any chat reset, the bot consolidates learnings (decisions, preferences, reusable steps, keeper drafts) into its memory, skills, or a file; only then reset. Cost per reply levels off because the app summarizes old history, so A20 $ figures are upper-bound estimates.
- **Spike guard: baseline + floors + freshness, or it cries wolf.** Compare each routine with its own trailing daily average, require a week of history, floor both runs and $, and never alert on stale snapshots. A backtest on a real fleet caught a webhook routine firing 9 times in an hour, a real retry loop, while daily routines with normal day-to-day variance stayed quiet. Cool down per routine and kind so one incident wakes once.
- **Dry-run must write nothing.** A daily check whose `--dry-run` seeded its own state file hid first-run behavior from tests; seeding is now an explicit `--seed`.
- **Calibrate estimates against the app's own Usage page.** Local replay proxies can be off by a large factor. One pasted reading gives burn rate and run-out; two give a correction factor. Keep the factor clamped and median-based, apply it only to the estimated part (never to exact coding $), and label calibrated numbers. With no readings, change nothing.
- **Give the owner one knob for noise** (quiet / normal / chatty) instead of five thresholds. Map it to overrides in config, so `normal` is exactly the defaults.
- **Lead the first chat with value:** a quick audit naming the top 1–3 likely burners before asking setup questions. Cap long chats in that list, since their $ is an upper bound and they'd crowd out fixable routines.
